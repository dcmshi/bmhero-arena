## Open items, highest value first

### 1. The arena doesn't FRAME (camera pose is fine)

**Correction to the previous handoff:** it claimed `gView.at` was ignored and the
view followed the player. That was **wrong**. At `ARENA_CAM_DIST=400` the picture
is a close-up of the arena *centre* with the player — 1100 units away at its
corner — nowhere in frame. That only happens if `at` is honoured. The dist sweep
separately proves our write drives the picture (zoom tracks it exactly), and the
camera-follow code that *does* overwrite `at` (`63F90.c`, dispatched by
`func_80076374`) runs **inside** `func_80024744`, so our post-update stamp wins.

**What's actually wrong, in numbers** (measured with `tools/shot_measure.py`):
the floor covers only **13% of the viewport at dist 2400** and hugs the corner
nearest the camera. Aiming further +X/+Z keeps increasing coverage — 12.9% at
offset 0, 28.8% at +475, 47.4% at +950, still rising — while aiming −X/−Z gives
**zero** floor. So the **drawn** floor is offset from the **collision** floor that
probe mode 7 measured. The collision raster alone could not have shown this.

**Three causes tested and ELIMINATED**, each by measurement:

| hypothesis | verdict |
|---|---|
| `gView.at` overwritten before the draw | No — dist-400 close-up shows the centre |
| level far clip plane (ZFAR) | No — MAP_NITROS_1 authors 8000; far corner is ~2400 |
| level-chunk view culling | No — radius 0→10 moved coverage 12.9%→13.7%, saturated |

The chunk-radius override was **reverted** rather than left in on a dead
hypothesis; the ZFAR override is kept as a guard for other maps with an honest
comment saying it wasn't the cause.

**Next step: RenderDoc** (installed). `qrenderdoc --python <script>` scripts the
analysis headlessly; `renderdoccmd capture` launches the game hooked. One capture
gives the real view matrix and the floor mesh's true world bounds, settling
"where is the drawn floor" directly instead of another hypothesis cycle.

Useful knobs, all no-rebuild: `ARENA_CAM_DIST`, `ARENA_CAM_AT_DX` / `_DZ`,
`ARENA_CAM_ZFAR`, `ARENA_RASTER_N` / `_STEP`.

## Traps that cost real time

1. **A failed build leaves the previous exe, and the soak tests it happily.**
   `build.ps1` retries once, but always confirm `BUILD OK` before trusting a probe.
2. **A gate can pass for the wrong reason.** `-Constant` on the rail camera's yaw
   passed because it happened to sit still; `-Absent` passes vacuously if the run
   never got in-arena. Assert on a value only *you* set, and pair `-Absent` with
   something positive.
3. **Measure the geometry, not the player.** Any measurement taken by moving the
   player is confounded by the very bounds you are checking. §8.15.
4. **Log which map you measured.** The render routine runs in every level, so
   `[capture]` fires wherever the draw gate opens — including the stage-select map.
5. **MSYS2 gcc fails silently** (exit 1, no diagnostic) when invoked by absolute
   path without its own `bin` on PATH. All the PS scripts prepend it.
6. **Export name collisions.** An export in `syms.ld` becomes a C symbol with the
   `(rdram, ctx)` signature — it must not share a name with the native
   implementation. Follow the `arena_export_*` shim convention.
7. **Mode gates are duplicated in `main.cpp`** — a new `ARENA_AUTO_BATTLE` mode
   must be added to BOTH the frontend-mash list and the launcher list, or the boot
   hangs before reaching the arena.
